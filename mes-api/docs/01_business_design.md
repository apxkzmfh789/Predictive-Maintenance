# 1단계 업무 설계 — 예지보전 경보·보전 작업지시

> 작성일: 2026-10-23 · 수정일: 2026-10-27 · 작성자: 이창우
> 대상: `mes-api` (Java 21 · Spring Boot · MyBatis · SQL Server) · DB 설계는 [02_db_design.md](02_db_design.md)

## 1. 목적과 범위

- Python 예측 결과(설비별 30분 내 고장 확률)를 받아 **경보 → 보전 작업지시 → 조치 완료 → 이력·집계**로 이어지는 현장 업무를 처리
- 구성

| 구성 | 역할 |
|---|---|
| Python 예측 (완료) | 센서 수집, 모델 학습, 예측 CSV·임계값 생성 |
| `mes-api` (이 문서) | 예측 적재, 경보 판정, 경보·작업지시 처리, 이력·집계 API |
| `pop-client` | C# WinForms 현장 단말. 경보 확인, 작업지시 생성·시작·완료 |

- 포함: 설비 기준정보, 예측 결과 적재, 경보 관리, 보전 작업지시, 상태 변경 이력, 집계
- 제외: 로그인·권한, 관리자 화면, 웹 화면, Docker, 서버 배포, 설비 직접 연동(MQTT 등)

## 2. 업무 흐름

```
① 설비 기준정보 등록 (3대, 설비 코드 = 예측 CSV의 machine_id)
② 예측 결과 적재: test_predictions.csv + metrics.json(임계값)
③ 경보 판정: 고장 확률 ≥ 경보 임계값이 연속 2회 → 경보 발생
   (같은 설비에 열린 경보가 있으면 새로 만들지 않고 갱신)
④ 작업자가 경보 확인
   ├─ 점검 필요 → ⑤ 보전 작업지시 생성
   └─ 헛경보    → 경보 종료 (사유: 오경보)
⑤ 작업지시: 대기 → 진행 → 완료 (담당자, 작업 유형, 결과 코드, 조치 내용 기록)
   진행 중에는 설비 상태 = 정비중
⑥ 작업지시 완료 → 연결된 경보 자동 종료 (사유: 조치 완료), 설비 상태 = 가동
⑦ 이력·집계 조회
```

## 3. 상태 정의

### 3.1 경보

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| `OPEN` 발생 | 시스템이 감지, 아직 확인 전 | `ACK` |
| `ACK` 확인 | 작업자가 확인 | `CLOSED` |
| `CLOSED` 종료 | 처리 끝 | 없음 |

- 종료 사유: `RESOLVED` 조치 완료 (작업지시 완료 시 자동) / `FALSE_ALARM` 오경보 (작업자가 직접 종료)

### 3.2 보전 작업지시

| 상태 | 의미 | 다음 상태 |
|---|---|---|
| `WAITING` 대기 | 생성됨, 작업 시작 전 | `IN_PROGRESS`, `CANCELED` |
| `IN_PROGRESS` 진행 | 작업 중 | `DONE` |
| `DONE` 완료 | 조치 끝 | 없음 |
| `CANCELED` 취소 | 시작 전 취소 | 없음 |

- 작업 유형: `INSPECTION` 점검 / `REPAIR` 수리 / `REPLACE` 교체
- 결과 코드: `NO_ISSUE` 이상 없음 / `ADJUSTED` 조정 / `PART_REPLACED` 부품 교체 / `REPAIRED` 수리

### 3.3 설비

| 상태 | 의미 |
|---|---|
| `RUNNING` 가동 | 기본 상태 |
| `MAINTENANCE` 정비중 | 연결된 작업지시가 진행 중 |

- 상태와 별도로 사용 여부를 둠. 사용하지 않는 설비는 적재에서 제외

## 4. 시각 기준

- 모든 시각은 한국 시간(KST)으로 저장. 예측 CSV의 `ts`(UTC)는 적재할 때 +9시간
- 시각은 두 종류

| 구분 | 뜻 | 쓰는 곳 |
|---|---|---|
| 데이터 시각 | 센서 데이터가 측정된 시각 (CSV의 `ts`) | 경보 판정 규칙 (R5, R7) |
| 처리 시각 | 시스템이 경보 생성·확인·작업 완료 등을 기록한 시각 | 집계 지표 |

- 예측이 파일 단위로 나중에 들어오기 때문에 두 시각이 다름

## 5. 업무 규칙

### 5.1 적재

| 번호 | 규칙 |
|---|---|
| R1 | 경보 임계값은 설정의 재정의 값이 있으면 그 값, 없으면 `metrics.json`의 `threshold` |
| R2 | 같은 설비·같은 데이터 시각의 예측은 먼저 들어온 값만 저장, 이후 중복은 건너뜀 |
| R3 | 사용하지 않는 설비의 예측은 건너뜀 |
| R4 | 경보 판정은 이번에 새로 저장된 예측만, 설비별 데이터 시각 순서로 처리 |

### 5.2 경보 발생 (데이터 시각 기준)

| 번호 | 규칙 |
|---|---|
| R5 | 임계값 이상이 **연속 2회** 이어지면 경보 발생. 데이터 간격이 2분을 넘으면 연속 횟수 초기화 |
| R6 | 같은 설비에 `OPEN`·`ACK` 경보가 있으면 새로 만들지 않고 최고 확률·마지막 감지 시각·감지 횟수만 갱신 |
| R7 | 경보 종료 후 **30분** 동안 같은 설비 경보 발생 금지. 종료 시점에 그 설비의 마지막 데이터 시각부터 계산 |

### 5.3 경보 처리

| 번호 | 규칙 |
|---|---|
| R8 | `OPEN` → `ACK` → `CLOSED` 순서만 허용. 확인 없이 바로 종료 불가 |
| R9 | 오경보 종료는 메모 필수. 진행 중(`WAITING`·`IN_PROGRESS`) 작업지시가 있으면 거부 |

### 5.4 작업지시

| 번호 | 규칙 |
|---|---|
| R10 | `ACK` 경보에서만 생성. 경보 하나당 진행 중 작업지시는 1개 |
| R11 | 완료 시 결과 코드와 조치 내용 필수. 연결된 경보는 `CLOSED(RESOLVED)`로 자동 종료 |
| R12 | 취소는 `WAITING`에서만 가능 |

### 5.5 설비

| 번호 | 규칙 |
|---|---|
| R13 | 작업 시작 시 `MAINTENANCE`, 완료 시 `RUNNING`. 취소는 시작 전이라 상태 변화 없음 |
| R14 | 설비 상태는 작업지시로만 바뀜. 설비 수정 API로는 이름·위치·사용 여부만 변경, 설비 코드와 상태는 변경 불가 |

### 5.6 공통

| 번호 | 규칙 |
|---|---|
| R15 | 모든 상태 변경은 이력에 기록 (대상, 이전 상태 → 이후 상태, 변경자, 시각, 메모). 시스템이 바꾸면 변경자 `SYSTEM` |
| R16 | 담당자·변경자는 이름 문자열로 저장 (로그인 없음) |
| R17 | 상태 변경은 현재 상태를 조건으로 건 UPDATE로 처리, 바뀐 행이 0건이면 거부 (동시 처리 방지) |
| R18 | 규칙에 어긋나는 요청은 거부하고 이유를 응답 |

### 5.7 설정값

| 이름 | 기본값 | 관련 규칙 |
|---|---|---|
| 경보 임계값 재정의 | 없음 (`metrics.json` 사용) | R1 |
| 발생 연속 횟수 | 2 | R5 |
| 재발생 금지 시간 | 30분 | R7 |

- 위치는 `application.yml` (D13)

## 7. 집계 지표

모두 처리 시각 기준

| 지표 | 계산 | 기간 기준 |
|---|---|---|
| 경보 수 | 생성된 경보 건수 | 경보 생성 시각 |
| 오경보율 | `FALSE_ALARM` 종료 ÷ 종료된 경보 | 경보 종료 시각 |
| 현장 확인 헛경보율 | 결과 `NO_ISSUE` ÷ 완료된 작업지시 | 작업 완료 시각 |
| 평균 확인 시간 | 경보 생성 → 확인 | 경보 확인 시각 |
| 평균 조치 시간 | 경보 확인 → 작업 완료 (작업지시 완료로 종료된 경보만) | 작업 완료 시각 |
| 비가동 시간 | 작업 시작 → 완료 시간의 합 | 작업 완료 시각 |

## 8. 설계 결정 기록

| 번호 | 결정 | 이유 |
|---|---|---|
| D1 | 열린 경보가 있으면 새로 만들지 않고 갱신 (R6) | 1분 단위 예측마다 경보가 쌓이는 경보 폭주 방지 |
| D2 | 작업지시는 작업자 확인 후 수동 생성 (R10) | 확률 모델은 헛경보가 많아 사람 판단을 거치는 것이 현실적 |
| D3 | 담당자는 이름 문자열 (R16) | 로그인을 범위에서 제외 |
| D4 | 발생 연속 2회 (R5) | 1분 단위 예측에서 한 번 튀는 값으로 경보가 뜨는 것 방지. 대가는 경보가 1분 늦어지는 것으로, 예측 범위 30분에 비해 작음 |
| D5 | 재발생 금지 30분 (R7) | 예측 범위(30분 내 고장)와 같은 길이. 같은 원인으로 경보가 반복되는 것 방지 |
| D6 | 경보 임계값을 모델 임계값과 분리 가능 (R1) | 모델 임계값은 1분 단위 예측의 비용 최소점이라 경보 운영에 맞는 값과 다를 수 있음. 기본값은 모델과 일관성을 위해 `metrics.json` |
| D7 | MTTR 대신 평균 확인 시간·평균 조치 시간 | MTTR은 실제 고장부터 복구까지의 지표인데, 이 시스템의 경보는 고장이 아니라 고장 예측 |
| D8 | 작업 결과를 코드로 받음 | `NO_ISSUE` 비율이 현장에서 확인된 헛경보율이 되어 임계값 조정의 근거가 됨 |
| D9 | 설비 상태를 작업지시와 연동 (R13) | 현장이 가장 먼저 보는 정보, 비가동 시간 집계의 근거 |
| D10 | 조건부 UPDATE로 상태 변경 (R17) | 두 작업자가 같은 경보를 동시에 처리하는 경우 방지 |
| D11 | 모든 시각을 KST로 저장 | 한 공장 시스템이고 일별 집계와 현장 화면이 한국 시간 기준. 해외 공장이 붙으면 `DATETIMEOFFSET`으로 변경 필요 |
| D12 | 경보 판정은 데이터 시각, 집계는 처리 시각 기준 | 예측이 파일로 나중에 들어와 두 시각이 다름. 판정을 처리 시각으로 하면 과거 데이터 적재 시 재발생 금지가 풀리지 않음 |
| D13 | 설정값은 DB가 아닌 `application.yml` | 관리자 화면이 범위 밖이라 값을 바꾸는 사람이 개발자뿐. 값 변경 시 재시작 필요. 설정 화면을 추가하면 설정 테이블 + API로 전환 |

- D14~D18은 테이블 구조 결정이라 [02_db_design.md](02_db_design.md)에 기록

## 9. 검증 계획

- 경보 규칙(연속 2회, 30분, 임계값)이 실제로 감당할 만한 경보 수를 내는지는 4단계 구현 후 확인
- 방법: 최근 14일 모델의 예측을 적재하고 설비당 하루 경보 수를 집계 API로 확인
- 경보가 너무 많으면 임계값 재정의(R1)로 조정하고 결과를 이 장에 기록
- 적중률 같은 정답 비교는 하지 않음. 정답은 DB에 저장하지 않고, 모델 성능 검증은 Python 파트에서 완료

## 10. 한계

- 실시간 수신이 아니라 파일 적재 방식이라, 적재하는 동안에는 경보 확인·종료가 일어나지 않음. 하루치를 한 번에 넣으면 설비당 경보가 1건으로 합쳐짐
- 헛경보 비율은 모델 성능에 달려 있고, 학습 데이터가 합성 데이터라 실제 설비와 다를 수 있음
- 로그인이 없어 담당자·변경자 이름을 검증할 수 없음

## 11. 미결 사항

- 적재 API 입력 방식: 파일 업로드 또는 서버 경로 (4단계)
- 시연용 구간 적재: 적재 API에 시간 구간(from/to)을 받아 나눠 적재하는 방식 검토 (4단계)
- 등록되지 않은 설비 코드가 CSV에 있을 때 파일 전체 거부 또는 해당 행만 건너뛰기 (4단계)
- CSV `machine_id`의 실제 값 확인 (3단계)
